# 한칸 0.7 · Android / iOS

식재료 라벨의 품목명·날짜 인식, 냉장고 재고, 레시피와 장보기 관리를 연결하는 한국어·영어 모바일 앱입니다. 현재 버전은 **0.7.0 베타**입니다.

## GitHub에서 시작하기

1. Node.js 22와 npm을 준비하고 `npm ci`를 실행합니다.
2. `.env.example`을 `.env.local`로 복사합니다. 본인의 Supabase URL과 publishable key를 넣거나 비워 두고 로컬 모드로 시작합니다. 관리자 키나 데이터베이스 비밀번호는 넣지 않습니다.
3. `npm test`로 자동 검사를 실행합니다. `npm run web`은 공통 UI의 브라우저 미리보기입니다.
4. Android는 Android Studio/JDK/SDK 환경에서 `npm run android`, iOS는 macOS/Xcode에서 `npm run ios`로 빌드합니다. 자체 OCR 모듈이 있어 네이티브 빌드가 필요합니다.

`modules/hankan-ocr/`의 Android/iOS 원본 코드는 저장소에 포함합니다. 루트의 생성된 `android/`, `ios/`, 설치 파일, 실제 환경설정과 서명키는 포함하지 않습니다. 기존 시험 APK를 업데이트하려면 관리자가 별도 보관한 동일한 서명키가 필요합니다.

자신의 **새 Supabase 프로젝트**에 한해 `supabase/migrations/001_pantry.sql`을 적용합니다. 기존 운영 프로젝트에 초기화 SQL을 재실행하지 마세요. 이 저장소의 공개는 앱스토어 출시나 GitHub Pages 배포를 의미하지 않습니다.


React Native + Expo 57 기반 실제 앱 프로젝트입니다. `App.jsx`는 React Native 컴포넌트이며, HTML 페이지를 WebView로 감싸는 방식이 아닙니다. 브라우저 미리보기는 같은 화면 코드를 React Native Web으로 실행합니다.

## 0.7 장보기에서 냉장고 등록

- 구매 예정/구매 완료/전체 탭과 장보기 검색, 상태별 개수를 추가했습니다. 레시피 재료는 현재 표시 언어 이름과 기존 한국어 이름으로 검색할 수 있습니다.
- 구매 완료 항목의 ‘냉장고 등록 화면 열기’로 이름과 추천 재료 분류를 가져옵니다. 새 재고 기록이며 저장 전 취소할 수 있습니다.
- 수량은 기본 1개로 시작합니다. 장보기 문구의 숫자를 임의 해석하지 않으며 날짜·개봉·메모는 가져오지 않습니다. 저장 전에 실제 포장 날짜, 수량과 보관 위치를 확인하세요.
- 장보기 목록은 등록 후에도 유지됩니다. 같은 항목에서 다시 저장하면 별도 재고가 등록되므로 이미 저장한 제품을 반복 등록하지 마세요. 여러 포장 제품은 날짜별로 나눠 등록할 수 있습니다.
- 현재 버전 0.7.0 / Android versionCode 7 / iOS buildNumber 7. 유료 API 추가 없음. 검증: RELEASE-0.7.md.

- 레시피에서 실제 사용한 제품과 수량을 확인한 뒤 재고에서 차감합니다. 부분 사용과 전량 사용, 마지막 차감 되돌리기를 지원합니다.
- 보유량 초과·중복 제출·확인 후 변경된 기록·동기화 충돌은 차감하지 않습니다. 날짜를 확인하지 않았거나 지난 제품도 제외합니다. 팩/개를 g/ml로 임의 환산하지 않습니다.
- 부족한 주재료를 장보기 목록에 추가하며, 같은 재료는 합칩니다. 직접 입력, 구매 체크, 삭제/마지막 삭제 복원, 재시작 후 보존을 지원합니다.
- 장보기 목록은 이 기기에 계정별로 저장합니다. 아직 다른 기기와 동기화되거나 기존 재고 백업에 포함되지 않습니다. 구매 체크는 냉장고 자동 등록이 아니며 날짜를 확인해 별도로 등록해야 합니다.
- 기존 6개 레시피는 재고가 없어도 열 수 있습니다. 재료 보유 여부와 필요한 수량 충족 여부는 다르며 양념/구매 수량은 직접 확인합니다.
- 한국어·영어 지원을 유지합니다. 현재 앱 버전 0.6.0, Android versionCode / iOS buildNumber 6입니다. 유료 API를 추가하지 않았습니다.
- 검증 및 한계는 RELEASE-0.6.md를 참고하세요.

## 0.5 버전 표시와 한국어·영어 (이전 버전)

- 상단에 항상 현재 버전(v0.5.0)을 표시합니다. 설정 > 앱 정보에서도 버전과 설치형 앱의 빌드 번호를 확인합니다. 화면 버전은 app.json에서 읽으며 Android versionCode / iOS buildNumber는 4입니다.
- 상단 EN/한국어 버튼 또는 설정 > 언어에서 바로 전환합니다. 최초 실행은 기기 언어(한국어/그 외 영어)를 따르며, 직접 선택한 언어는 기기에 저장합니다. 로그인할 필요가 없습니다.
- 재료 목록·등록·사진 인식 안내·레시피·로그인·동기화·백업·오류·기한 알림을 번역했습니다. 언어를 바꾸면 이미 예약한 알림도 선택한 언어로 다시 예약합니다.
- 저장한 재료 이름·메모 및 사진에서 읽은 원문은 번역하지 않습니다. 내부 보관 위치·단위·재료 식별값은 유지하므로 기존 재고·백업·동기화 데이터와 호환됩니다.
- 영어로 입력한 milk, eggs, tofu, green onion 등의 이름을 기존 추천용 재료 분류에 연결합니다. 제품 사진 자체를 새로운 다국어 모델로 학습한 변경은 아닙니다.
- src/locales/catalog.mjs가 번역 리소스이고 src/i18n.mjs가 언어 저장·문구 치환을 담당합니다. 추가 언어를 넣을 때는 번역 리소스와 src/i18n.mjs의 언어·날짜·수량 처리, 네이티브 메타데이터를 확장하고 해당 언어 검사를 추가합니다.
- Android 앱 이름 및 iOS 앱 이름·사진/카메라 권한 안내의 한국어·영어 리소스를 구성했습니다. 운영체제 권한 창은 기기 언어를 따를 수 있습니다.
- 검증과 미검증 범위: RELEASE-0.5.md. 추가 유료 API·서버·번역 요청은 없습니다.

## 0.4 품목명과 연속 등록 (이전 버전)

현재 개발 작업본은 `C:/Users/gnsdu/Desktop/dev/Hankan`입니다. 이전 Documents/Codex 및 날짜별 복사본은 과거 작업 보관용입니다.

- 브랜드가 크다는 이유만으로 자동 입력하지 않습니다. 제품명·상품명·품명 표시를 먼저 찾고 원재료/영양정보의 다음 줄까지 제외합니다. 불확실하거나 여러 이름이 경쟁하면 후보 선택을 요청합니다.
- 저지방 우유·냉동 만두 같은 실제 제품명을 메타데이터로 잘못 제외하던 규칙을 수정했습니다. 분리된 제품명 줄·띄어진 글자·라벨 오른쪽 값도 후보 추출에 사용합니다.

- 등록 화면을 이름 확인 → 날짜 확인 → 보관 정보 순서로 정리했습니다. 사진/영역 설정은 인식 후 접어 입력 결과를 먼저 볼 수 있습니다.
- ‘저장하고 다음 재료 등록’은 새 기록 번호를 만들고 이름·날짜·확인 상태를 초기화하며 보관 위치만 이어받습니다.
- ‘다시 산 재료’는 이전 이름·추천 재료·단위·보관 위치를 재사용합니다. 수량은 1로 시작하고 날짜·개봉 상태·메모는 복사하지 않습니다.
- 네이티브 OCR 함수 인자가 변경되었으므로 0.4 APK 전체 업데이트가 필요합니다. Android versionCode는 3, 패키지는 com.hankan.app이며 기존 개발 서명을 유지합니다.

이름 후보의 점수는 제품명 표시와 문맥에 따른 규칙이며 인식 정확도 확률이 아닙니다. 브랜드 목록은 보조 필터이고 모든 브랜드를 아는 제품 데이터베이스가 아닙니다. 사용자가 실패한 실제 사진은 제공되지 않았으므로 실물 포장 사진의 정확도는 추가 확인이 필요합니다. 유료 AI API나 사진 서버 업로드는 추가하지 않았습니다.

검증 결과는 `RELEASE-0.4.md`에 기록합니다.

Android의 점진 빌드에서 `.mjs` 인식 규칙 변경이 빠지지 않도록 `plugins/withOcrBuildInputs.cjs`를 등록했습니다. `expo prebuild`로 Android 프로젝트를 다시 생성해도 이 설정이 반영됩니다.

## 0.3 사진 인식 개선 (이전 버전)

- 촬영/사진 선택 직후 품목명과 날짜를 자동으로 읽어 빈 입력란을 채웁니다. 이름 후보를 선택하거나 수정할 수 있습니다. 앞면의 제품명과 뒷면의 날짜를 나눠 촬영해도 이름을 덮어쓰지 않습니다.
- 기존 1,800px JPEG 단일 인식을 최대 3,200px/600만 화소 PNG 전처리로 변경했습니다. 날짜가 없으면 Android의 별도 Latin 모델과 회색조·대비 보정, 겹치는 세 영역 확대를 순서대로 시도합니다. 모든 모델은 APK에 포함되며 사진을 전송하거나 유료 API를 호출하지 않습니다. 사진의 실제 글자 크기·흔들림·반사에 따른 한계는 남습니다.
- 전체/위/가운데/아래/중앙 확대를 선택하면 선택 영역을 표시합니다. 90도 회전 및 네이티브 사진 선택기의 영역 자르기를 지원합니다.
- `2026 09 20`, `260920`(날짜 라벨이 있는 경우), 전각 숫자, 쉼표 구분, `2O26.O9.2O` 등 숫자 혼동과 줄바꿈된 날짜 라벨을 처리합니다. 숫자 보정·두 자리 연도는 확인 표시를 붙입니다. 연도가 없는 월/일은 임의로 현재 연도를 넣지 않습니다.
- 제품명/품목명 표시와 글자 크기·식품 이름을 사용해 후보를 추출합니다. 영양정보/원재료/보관방법은 제외하며, 정확한 제품명 인식률은 실제 포장 사진으로 추가 검증해야 합니다. 식품 자체만 찍고 라벨이 없으면 품목을 알아내는 이미지 분류 기능은 아닙니다.
- 글자를 전혀 못 읽은 경우와 글자는 읽었지만 날짜가 없는 경우를 구분하고, 원문을 펼쳐 확인할 수 있습니다. 날짜 직접 확인 전 저장 차단은 유지합니다.
- 검사: 자동 테스트 11개 통과, Android release APK 빌드 및 서명 확인, Android/iOS/Web JS 번들 생성, 웹에서 합성 라벨의 품목명·날짜 자동 입력과 제조일 선택 차단/확인 전 저장 차단 확인. 사용자가 실패한 원본 사진은 아직 제공되지 않아 같은 사진의 해결 여부와 Android 실기기 정확도는 확인하지 않았습니다. iOS 네이티브 모듈은 이 Windows 환경에서 빌드하지 않았습니다.

Android 0.3은 versionCode 2이며 0.2와 같은 개발 서명을 사용합니다. 기존 앱을 삭제하지 않고 APK를 열어 업데이트합니다. 앱 삭제 시 동기화하지 않은 로컬 기록은 사라질 수 있습니다.

## 연결된 무료 서버

- 서비스: Supabase / Hankan 조직 / hankan 프로젝트 / Free / 서울(ap-northeast-2)
- 프로젝트 대시보드: https://supabase.com/dashboard/project/rpgafcqblnakloyubben
- 이 작업 폴더의 `.env.local`에 앱용 공개 URL과 publishable key를 설정했습니다. 비밀번호나 service_role/secret key는 앱에 넣지 않습니다.
- `supabase/migrations/001_pantry.sql`을 실제 프로젝트에 적용했습니다. 이 파일은 새 프로젝트 초기화용이므로 이미 적용한 서버에 다시 실행하지 않습니다.
- 로그인한 사용자는 자기 행만 읽을 수 있습니다. 쓰기는 소유자 확인·자료 검증·버전 비교를 수행하는 `sync_pantry` RPC로만 가능합니다. 테이블의 익명 접근과 직접 수정 권한은 없습니다.
- 실제 서버에 임시 계정/재료를 트랜잭션 안에서 넣어 저장과 계정 분리를 확인한 뒤 롤백했습니다. 실제 사용자 로그인/이메일 인증과 두 휴대폰 간 동기화는 별도 검증해야 합니다.

Supabase 관리용 ChatGPT 계정과 **한칸 앱의 이메일 계정은 별개**입니다. 앱의 로그인 화면에서 회원가입하고 메일 인증을 마친 뒤 로그인합니다. 기본 메일 서비스는 테스트용이며 발송 대상/빈도 제한이 있어, 외부 사용자 공개 전에는 별도 SMTP 또는 소셜 로그인을 설정해야 합니다. 이메일 인증을 꺼서 우회하는 방식은 사용하지 않았습니다.

인증의 기본 복귀 주소는 `hankan://auth`이며, 로컬 미리보기 `http://127.0.0.1:8770`을 별도로 허용합니다. 앱은 PKCE 코드를 교환하도록 연결했습니다. 다른 기기에서 메일을 열어 코드 교환을 마치지 못했더라도, 메일 인증 후 이메일과 비밀번호로 로그인할 수 있습니다.

## 구현한 기능

- Android/iOS 공통 재료 목록·등록·수정·삭제 취소·검색·보관 위치 필터.
- 한국어/영어 날짜 인식. Android는 번들된 Google ML Kit 한국어·Latin 모델, iOS는 Apple Vision을 쓰는 로컬 Expo 모듈입니다. 웹 확인용으로는 기존 Tesseract 엔진을 유지합니다.
- 소비기한·유통기한 후보를 확인한 후 저장. 제조·포장일은 선택을 막고, 표시 종류가 불명확한 날짜는 따로 표시합니다.
- 재고와 변경 내역은 기기에 먼저 저장합니다. 로그인 후 변경 또는 앱 재진입 시 서버 동기화를 시도하며 수동 재시도도 가능합니다.
- 계정별 로컬 저장 공간 분리. 로그인 전 기록은 사용자가 가져오기를 선택해야 계정에 복사됩니다. 예시 재료는 이 과정에서 제외합니다.
- 두 기기의 동시 수정은 사용자 선택 전까지 전송을 멈추고 두 내용을 보여줍니다. 전송 중 새 수정이 생겨도 보존하며, 같은 요청 재시도로 데이터가 중복되지 않습니다.
- 기기 내 날짜 알림: 3일 전·1일 전·당일 오전 9시, 같은 날 여러 재료를 묶음. 사용자가 권한을 허용하고 켰을 때만 예약합니다. 다음 50개 일정까지 예약하고 앱 실행·재고 변경 때 갱신합니다. 기기 절전/방해금지 설정에 따라 전달이 달라질 수 있습니다.
- 남은 재료를 이용하는 6개 자체 레시피, 부족한 재료와 분량·조리법.
- JSON 재고 백업과 중복을 제외한 복원. 이전 웹 시제품 `hankan-v1` 백업도 가져올 수 있습니다.

## 실행

Node.js 22 이상과 npm을 사용합니다.

```sh
npm ci
npm start
```

다른 환경으로 소스를 옮겼다면 `.env.example`을 `.env.local`로 복사하고 해당 프로젝트의 공개 연결 정보를 입력합니다. `npm run web`은 공통 UI와 로그인·동기화·웹 OCR을 브라우저에서 확인합니다.

Expo Go에서는 목록과 카메라 등 일부 기능을 확인할 수 있지만 **자체 네이티브 OCR 모듈은 한칸 앱 빌드가 필요**합니다. 앱에서 지원 여부를 확인해 직접 입력을 안내합니다.

Android 로컬 빌드:

```sh
npx expo prebuild --platform android --no-install
npx expo run:android
```

이번 작업에서 `assembleRelease`로 Android 64비트(arm64-v8a) 테스트 APK를 만들었습니다. Android 7(API 24) 이상을 대상으로 하며, 앱 버전은 0.5.0입니다. JavaScript가 APK에 포함되어 있어 별도 Metro 개발 서버 없이 실행하는 빌드입니다. 기본 개발용 서명을 사용했으며 실제 휴대폰 설치/실행 검증을 마쳤다는 뜻은 아닙니다. 결과 파일은 `C:/Users/gnsdu/Desktop/dev/outputs/hankan-downloads/hankan-0.5-android-test.apk`입니다.

Windows에서 폴더 경로가 길면 CMake 빌드가 실패할 수 있습니다. 이 경우 소스와 의존성을 짧은 임시 경로에 복사해 빌드하고, 기존 `.cxx`/`.gradle`/네이티브 `build` 캐시는 복사하지 않습니다. npm 패키지 내부의 `dist`와 JavaScript `build` 폴더는 필요합니다.

iOS 빌드는 macOS와 Xcode가 필요합니다. 이 Windows 작업 환경에서는 iOS JavaScript 번들까지 검증하고, Swift 모듈의 기기 실행은 검증하지 않았습니다. macOS에서 `npx expo run:ios`로 네이티브 모듈을 포함해 빌드합니다.

앱 식별자 `com.hankan.app`은 개발용 초안입니다. 앱스토어 제출 전 소유한 고유 식별자, 서명 인증서, 앱 아이콘과 개인정보 안내를 확정해야 합니다. 로컬 Android 시험 빌드는 Expo의 개발용 서명을 사용하며 스토어 제출용 서명이 아닙니다.

## 테스트와 아직 남은 검증

`npm test`는 실제 PostgreSQL 엔진인 PGlite에서 SQL을 실행해 권한 분리, 원자적 저장, 재시도, 동시 수정, 삭제 동기화, 오프라인 보존을 검증합니다. 별도로 날짜 파싱/확인과 알림 일정을 검사합니다.

`node --env-file=.env.local scripts/check-server.mjs`로 실제 공개 API에서 비로그인 테이블 조회와 동기화가 401로 차단되는 것을 확인할 수 있습니다.

실제 Supabase 서버 스키마와 임시 데이터 저장도 검사했습니다. 공통 웹 화면에서 사진 인식→확인 전 저장 차단→확인 후 저장→새로고침 복원을 검사했습니다.

휴대폰 사진의 반사·도트 인쇄, Android/iOS 실기기 OCR 정확도, 앱 종료 후 알림 전달, 실제 이메일 인증과 계정 로그인, 두 휴대폰의 동기화는 출시 전 검증 항목입니다. Windows에서 iOS 앱을 빌드하거나 실행했다고 주장하지 않습니다.

사진은 서버에 업로드하지 않습니다. 휴대폰 사진 선택기는 앱 캐시에 사진 사본을 만들 수 있고, 직접 전처리한 OCR 임시 이미지는 인식 후 삭제합니다. 재료 정보는 로컬 저장 공간과 로그인한 계정의 서버에 저장합니다. 로컬 앱 데이터 삭제에 대비해 서버 동기화와 별도 백업을 확인하세요.

현재 재료는 100개 제한입니다. 삭제 내역은 오래 오프라인인 기기에 삭제를 전파하기 위해 서버에 남기는 방식이며 자동 정리 정책은 아직 없습니다. 가족 공유, 비밀번호 재설정 화면, 계정 삭제 화면, 서버 백업 자동화, 앱스토어 제출은 이후 작업입니다.
